十二、面试核心口径速查（Argus 方向）

**Q：25% 召回率提升怎么测的？**
> 我设计了 10 个覆盖 3 类意图（专有名词、概念语义、多条件复合）的测试 query，用 `pg_trgm` 相似度作为自动相关性判定 ground truth。分别跑纯向量检索和混合检索+RRF 两种配置，对比 Precision@5、Recall@5、MRR。结果混合检索在专有名词查询上提升最明显（平均 +40%），关键词弥补了向量对低频词召回不足。总体 Recall@5 提升 25%，评估报告在项目文档里能现场跑。

**Q：Query Planning 为什么默认关闭？**
> 这是配置化开关的设计。DIRECT/REWRITE/DECOMPOSE 需要额外 LLM 调用，有延迟和成本。简单 query 直出（DIRECT）性价比更高。默认关闭是保障系统稳定性的兜底策略，当业务需要复杂查询拆解时可以通过配置开启。

**Q：RRF 融合后为什么加重排序器？**
> RRF 只做了粗排（基于排名位置融合），没有真正理解 query 和文档内容的语义匹配。重排序器用 LLM 评估细粒度相关性，能把"排名靠前但内容不相关"的结果压下去。当前用 LLM 是因为轻量、不需要引入 Python 依赖，只重排序 top-10 减少延迟。未来数据量大时考虑迁移到 cross-encoder（如 bge-reranker）。

**Q：pg_trgm 和 Elasticsearch 相比为什么选它？**
> 项目初期基于部署复杂度考虑。pg_trgm 是 PostgreSQL 扩展，不需要额外中间件，和向量检索在同一实例里方便混合查询。如果数据规模超百万或需要复杂中文分词，会考虑升级到 `pg_fulltext` 或 Elasticsearch。当前阶段 pg_trgm 性价比最高，已加 GIN 索引优化查询性能。

**Q：异步 ETL 失败怎么处理？**
> 使用 Spring Event + `@Async` + `@Retryable`（3 次回退，2s/4s/8s）+ `@Recover` 标记 FAILED。失败触发事件监听，重试耗尽后落库标记失败状态，支持人工重新触发。解析、分块、向量化每个步骤独立失败可定位。

**Q：混合检索怎么保证数据隔离？**
> 向量检索通过 `FilterExpressionBuilder` 在 `groupId` 上加过滤条件，关键词检索直接在 SQL 的 WHERE 子句里限制 `groupId`。同时有防御性校验：检索前校验 groupId 与当前用户所属 group 一致，防止跨租户泄漏。
