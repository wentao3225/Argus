# 消息队列技术选型与应用场景

## 1. 消息队列概述

消息队列（Message Queue，MQ）是一种异步通信机制，生产者将消息发送到队列，消费者从队列中读取消息并处理。消息队列是分布式系统中实现服务解耦、流量削峰和异步处理的核心基础设施。

### 1.1 核心概念

- **生产者（Producer）**：发送消息的应用程序
- **消费者（Consumer）**：接收并处理消息的应用程序
- **主题（Topic）**：消息的逻辑分类，生产者将消息发布到主题，消费者订阅感兴趣的主题
- **分区（Partition）**：主题的物理细分，每个分区是一个有序的消息序列
- **偏移量（Offset）**：消息在分区中的位置标识，消费者通过偏移量记录消费进度
- **消费者组（Consumer Group）**：一组消费者共同消费一个主题，每条消息只被组内的一个消费者处理

### 1.2 消息模型

**点对点模型**：消息被发送到队列，只有一个消费者能消费该消息。消费者处理完成后发送确认（ACK），消息从队列中移除。适用于任务分发场景。

**发布订阅模型**：消息被发送到主题，所有订阅该主题的消费者都会收到消息的副本。适用于事件广播场景。

## 2. 主流消息队列对比

### 2.1 Apache Kafka

Kafka 是一个分布式流处理平台，最初由 LinkedIn 开发，现为 Apache 顶级项目。Kafka 的核心设计目标是高吞吐量和水平扩展能力。

Kafka 的核心特性：
- **吞吐量极高**：单集群可支持每秒百万级消息
- **持久化存储**：消息持久化到磁盘，支持消息回溯
- **分区机制**：通过分区实现并行消费和水平扩展
- **消费者组**：支持消费者组实现负载均衡

Kafka 适用场景：
- 大数据流处理（日志收集、事件流）
- 实时数据管道
- 高吞吐量的消息传递
- 需要消息回溯的场景

```properties
# Kafka 生产者配置
bootstrap.servers=kafka1:9092,kafka2:9092,kafka3:9092
acks=all
retries=3
batch.size=16384
linger.ms=5
compression.type=lz4
```

Kafka 的 `acks` 参数控制消息确认机制：
- `acks=0`：生产者不等待确认，吞吐量最高但可能丢消息
- `acks=1`：等待 Leader 副本确认，平衡性能和可靠性
- `acks=all`：等待所有 ISR 副本确认，最可靠但延迟最高

### 2.2 RabbitMQ

RabbitMQ 是一个实现了 AMQP（Advanced Message Queuing Protocol）协议的消息代理。它以可靠性高、功能丰富著称，支持复杂的路由规则。

RabbitMQ 的核心特性：
- **灵活的路由**：通过 Exchange 和 Binding Key 实现复杂的消息路由
- **消息确认**：支持手动 ACK 和自动 ACK 两种模式
- **死信队列**：处理消费失败的消息
- **优先级队列**：支持消息优先级

RabbitMQ 的 Exchange 类型：
- **Direct**：精确匹配 Routing Key
- **Topic**：通配符匹配 Routing Key（`*` 匹配一个单词，`#` 匹配零或多个单词）
- **Fanout**：广播到所有绑定的队列
- **Headers**：基于消息头属性匹配

RabbitMQ 适用场景：
- 企业级应用的消息传递
- 需要复杂路由规则的场景
- 对消息可靠性要求极高的场景
- 中小规模的消息处理

```java
// RabbitMQ 消息确认
channel.basicConsume(queueName, false, (tag, delivery) -> {
    try {
        processMessage(delivery.getBody());
        channel.basicAck(delivery.getEnvelope().getDeliveryTag(), false);
    } catch (Exception e) {
        channel.basicNack(delivery.getEnvelope().getDeliveryTag(), false, true);
    }
});
```

### 2.3 RocketMQ

RocketMQ 是阿里巴巴开源的分布式消息中间件，现为 Apache 顶级项目。它在高可用和消息可靠性方面表现优秀，特别适合电商和金融场景。

RocketMQ 的核心特性：
- **事务消息**：支持分布式事务的最终一致性
- **延迟消息**：支持 18 个级别的延迟投递
- **消息重试**：消费失败时自动重试，支持自定义重试策略
- **消息轨迹**：追踪消息的完整生命周期

RocketMQ 适用场景：
- 电商订单处理
- 分布式事务（最终一致性）
- 延迟任务（如订单超时取消）
- 金融级消息可靠性

### 2.4 选型建议

| 特性 | Kafka | RabbitMQ | RocketMQ |
|------|-------|----------|----------|
| 吞吐量 | 百万级/秒 | 万级/秒 | 十万级/秒 |
| 延迟 | 毫秒级 | 微秒级 | 毫秒级 |
| 可靠性 | 高 | 高 | 很高 |
| 消息回溯 | 支持 | 不支持 | 支持 |
| 事务消息 | 不支持 | 不支持 | 支持 |
| 延迟消息 | 不支持 | 插件支持 | 原生支持 |
| 运维复杂度 | 高 | 中 | 中 |

选型决策树：
1. 需要高吞吐量和消息回溯 → Kafka
2. 需要复杂路由和低延迟 → RabbitMQ
3. 需要事务消息和延迟消息 → RocketMQ
4. 小团队简单场景 → RabbitMQ（最容易上手）

## 3. 消息队列的可靠性保证

### 3.1 消息丢失的三个环节

消息可能在三个环节丢失：

**生产端丢失**：生产者发送消息后，网络故障导致消息未到达 Broker。解决方案是开启发送确认（ACK）和本地消息表。

**Broker 端丢失**：消息写入 Broker 后，Broker 宕机导致内存中的消息丢失。解决方案是消息持久化到磁盘，并设置副本因子（replication factor）。

**消费端丢失**：消费者收到消息后，处理过程中宕机，但已发送 ACK。解决方案是手动确认，处理完成后再发送 ACK。

### 3.2 幂等消费

消息队列通常保证"至少一次投递"（at-least-once），这意味着消费者可能收到重复消息。实现幂等消费的方法：

- **数据库唯一约束**：利用数据库的唯一键约束防止重复插入
- **Redis 去重**：将已处理的消息 ID 存入 Redis，处理前检查是否已存在
- **状态机**：通过状态机控制业务流程，确保重复消息不会导致状态错误

### 3.3 顺序消费

某些业务场景要求消息按顺序处理（如订单状态变更）。实现顺序消费的方法：

- **分区有序**：将需要保证顺序的消息发送到同一个分区（如按订单 ID 取模）
- **单消费者**：每个分区只分配一个消费者
- **内存队列**：消费者内部使用内存队列保证处理顺序

## 4. 高级应用场景

### 4.1 事件驱动架构

事件驱动架构（Event-Driven Architecture，EDA）以事件为核心，通过消息队列将事件生产者和消费者解耦。事件代表系统中发生的状态变更，如"订单已创建"、"支付已完成"。

事件风暴（Event Storming）是设计事件驱动架构的方法论，通过领域事件、命令和聚合来建模业务流程。

### 4.2 CQRS 模式

CQRS（Command Query Responsibility Segregation）将读写操作分离到不同的模型中。写操作通过命令总线发送到写模型，写模型发布领域事件，读模型订阅事件并更新查询视图。

CQRS 与消息队列的结合：
1. 用户发送命令（如创建订单）
2. 写模型处理命令并发布事件
3. 消息队列将事件传递给读模型
4. 读模型更新查询视图

### 4.3 Saga 模式

Saga 模式用于管理分布式事务。一个 Saga 由一系列本地事务组成，每个本地事务更新自己的数据库并发布事件，触发下一个本地事务。如果某个步骤失败，Saga 执行补偿操作回滚已完成的步骤。

编排式 Saga 通过 Saga 协调器控制流程：
1. 协调器发起第一步本地事务
2. 第一步成功后，协调器发起第二步
3. 如果第二步失败，协调器发起第一步的补偿操作

### 4.4 死信队列与重试策略

死信队列（Dead Letter Queue，DLQ）用于存储消费失败的消息。当消息重试次数超过阈值时，消息被发送到死信队列，由专门的处理程序进行人工干预或自动修复。

合理的重试策略应该包含：
- 指数退避：每次重试的间隔时间递增（如 1s、2s、4s、8s）
- 最大重试次数：避免无限重试（通常 3-5 次）
- 告警通知：超过重试次数后发送告警
- 死信队列：最终失败的消息进入死信队列等待处理
