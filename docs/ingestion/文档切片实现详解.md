# Argus 当前文档切片实现详解

> 适用读者：已经理解上传、异步摄入、reader、parser、清洗主链路，现在想专门把“文档正文是怎么被切成检索 chunk 的”彻底看明白的开发者。
>
> 本文只讨论 ingestion 阶段的文档切片，不讨论上传分片。

---

## 1. 一句话结论

Argus 当前使用的是一种结构感知的分层切片策略。

它不是上来就按固定长度硬切，而是遵循下面这条降级链路：

```text
标题边界优先
    ↓
段落边界优先
    ↓
句子边界优先
    ↓
超限后再按长度预算硬切
    ↓
相邻片段再做贪心合并
    ↓
最终 chunk 带 overlap 和元数据落库
```

所以这套实现的关键词不是“固定长度”，而是：

- 结构优先
- 逐级降级
- 预算约束
- overlap 衔接
- 可回溯元数据

## 2. 这份文档回答什么问题

这份文档主要回答 7 个问题：

1. 当前切片是在摄入链路的哪个阶段执行的。
2. `StructureAwareChunkTransformer` 的输入和输出分别是什么。
3. 它内部到底按什么顺序切。
4. 标题、段落、句子、硬切之间的关系是什么。
5. overlap 是怎么加的。
6. chunk 生成后又是怎么落库的。
7. 这套实现当前的优点、边界和适用场景分别是什么。

## 3. 在主链路里的位置

切片不单独对外暴露接口，它是 ETL 主处理器内部的一步。

主路径在：

- `Argus-backend/src/main/java/com/argus/rag/ingestion/service/EtlDocumentIngestionProcessor.java`

当前控制顺序是：

```text
reader.get()
    ↓
textCleanupTransformer.apply()
    ↓
persistPreviewText()
    ↓
chunkTransformer.apply()
    ↓
chunkService.saveChunkDocuments()
    ↓
vectorService.ingestChunks()
```

也就是说，Argus 当前切的是“解析并清洗后的正文文本”，不是原始文件二进制，也不是上传时的文件传输分片。

这里要刻意区分两个概念：

1. 上传分片：为了解决大文件上传、断点续传、秒传复用。
2. 文档切片：为了让后续向量检索和混合检索拥有更合适的语义粒度。

两者完全不是一回事。

---

## 4. 代码落点

当前和文档切片直接相关的核心代码有 4 个：

1. `Argus-backend/src/main/java/com/argus/rag/ingestion/service/EtlDocumentIngestionProcessor.java`
作用：决定什么时候开始切。

2. `Argus-backend/src/main/java/com/argus/rag/ingestion/service/pipeline/transformer/StructureAwareChunkTransformer.java`
作用：决定怎么切。

3. `Argus-backend/src/main/java/com/argus/rag/ingestion/service/pipeline/transformer/ChunkingProperties.java`
作用：提供切片预算配置。

4. `Argus-backend/src/main/java/com/argus/rag/ingestion/service/pipeline/ChunkService.java`
作用：把切好的 chunk 转成 `document_chunks` 表记录并落库。

如果只想找“算法主体”，就看 `StructureAwareChunkTransformer`。
如果想看“完整落地链路”，这 4 个文件要一起看。

## 5. 当前实际配置

配置类默认值在：

- `ChunkingProperties.java`

默认值是：

- `targetTokens = 500`
- `maxTokens = 800`
- `overlapTokens = 80`

但当前开发环境实际生效值在：

- `Argus-backend/src/main/resources/application-dev.yml`

当前 dev 配置是：

```yaml
ingestion:
  chunking:
    target-tokens: 240
    max-tokens: 320
    overlap-tokens: 32
```

所以当前项目在本地开发环境里，更接近下面这组含义：

- 一个 chunk 的理想大小大约是 240
- 单块最大不要超过 320
- 相邻块默认保留 32 的 overlap

需要注意：这里的 token 不是严格 tokenizer 计算，而是字符级近似估算。

`StructureAwareChunkTransformer` 里把：

```java
private static final int CHARS_PER_TOKEN = 1;
```

并且 `estimateTokens(text)` 目前直接返回 `text.length()`。

所以这里更准确的理解是：

- 当前实现把“字符数”近似当作“token 数”使用
- 这是一种工程上的简化，不是精确分词结果

## 6. 总体算法思路

当前类的主入口是：

- `StructureAwareChunkTransformer.apply(List<Document> documents)`

它对每个 Spring AI `Document` 单独处理，再把结果汇总成新的 chunk `Document` 列表。

整体流程可以压成下面这张图：

```text
输入 Document
    ↓
chunkDocument(document)
    ↓
splitBySections(text)
    ↓
对每个 section 执行 splitSection(text, section)
    ↓
如果 section 不超限，直接保留
    ↓
如果超限，按段落拆
    ↓
段落再超限，按句子拆
    ↓
句子再超限，按长度预算硬切
    ↓
mergePieces() 贪心合并
    ↓
buildDocuments() 追加 overlap 并生成元数据
    ↓
输出 chunk Document 列表
```

这个顺序非常重要，因为它体现了当前策略的基本哲学：

优先保留自然结构边界，实在保不住了才降低粒度继续切。

---

## 7. 第一步：按标题切 section

入口方法：

- `splitBySections(String text)`
- `collectHeadings(String text)`

### 7.1 标题识别规则

当前只识别 Markdown ATX 标题，也就是这种形式：

```text
# 一级标题
## 二级标题
### 三级标题
```

内部使用的正则是：

```java
(?m)^(#{1,6})\s+(.+)$
```

也就是说：

- 只识别 1 到 6 个 `#` 开头的标题
- 标题后必须有空格
- 主要面向 Markdown 或被 parser 规整成 Markdown 风格的文本

### 7.2 不会误把代码块里的 # 当标题

`collectHeadings` 不是简单全局正则扫描，而是逐行遍历，并配合：

- `openFence(String line)`
- `isClosingFence(String line, Fence fence)`

它会先识别三反引号或三波浪号代码块，代码块打开后，内部的 `#` 行不会参与标题解析。

这意味着像下面这种内容不会被误切：

```text
```java
# 这不是 Markdown 标题
```
```

对技术文档、接口文档、代码示例型文档来说，这个保护很有价值。

### 7.3 没有标题时怎么办

如果全文没有识别到标题：

- 整篇文本会被当成一个 section

这保证了即使是纯 TXT 或结构很弱的文本，后续逻辑仍然能继续运行。

### 7.4 第一个标题前的内容不会丢

如果正文最前面有引言、摘要、前置说明，而第一个标题后面才开始正文主体：

- 这段前导文本会作为一个“无标题 section”保留下来

这由 `appendLeadingSection(...)` 完成。

---

## 8. 第二步：section 先整块判断，再逐级降级拆分

入口方法：

- `splitSection(String text, Section section)`

它的判断很直接：

1. 如果一个 section 的估算长度没有超过 `maxTokens()`，直接作为一个 chunk 输出。
2. 如果 section 超限，才继续拆细。

这一步的意义很大：

- 能完整保留一个章节时，就不轻易切碎。
- 当前策略不是“必须切成统一长度”，而是“尽量整块保留语义结构”。

---

## 9. 第三步：先按段落拆

入口方法：

- `splitByParagraphs(String text, Section section)`

段落边界依赖的是连续空行，内部正则是：

```java
\n\s*\n+
```

也就是：

- 一个或多个空白行被视为段落分隔
- 非空白连续文本会被看成同一段落

如果 section 很长，它会先被拆成若干 paragraph 范围。

这一步非常符合一般文档的自然阅读边界，因为段落通常比固定字符切分更能保持上下文完整。

---

## 10. 第四步：段落还大，再按句子拆

入口方法：

- `splitBySentences(String text, ChunkRange range)`

当前句子边界是根据标点字符判断：

```text
。！？；!?;
```

也就是说，它兼顾了中英文句子结束符号。

这一步说明当前实现至少考虑了：

- 中文句号、问号、叹号、分号
- 英文问号、叹号、分号

如果一个段落依然太长，会被继续打散成句子级片段。

这里仍然属于“保自然边界”的思路，而不是立刻按长度硬截断。

---

## 11. 第五步：再不行才硬切

入口方法：

- `splitByTokenBudget(String text, ChunkRange range)`

当前实现会按：

```text
maxTokens * CHARS_PER_TOKEN
```

作为固定步长进行硬截断。

由于当前 `CHARS_PER_TOKEN = 1`，所以在 dev 环境里，本质上接近：

- 每次最多按 320 字符向前推进一刀

这一步是最后兜底，不是常态主策略。

换句话说，硬切在 Argus 当前实现里的角色是：

- 保证再极端的超长文本也能被切出来
- 防止长段或长句导致整条链路失控

---

## 12. 第六步：拆完后还要再合并

入口方法：

- `mergePieces(String text, List<ChunkRange> pieces)`
- `canMerge(String text, ChunkRange current, ChunkRange next)`

这一层很容易被忽略，但它其实是当前切片效果是否“自然”的关键。

原因是前面按段落或句子拆完之后，可能会得到很多小片段。如果直接输出，会出现：

- chunk 太碎
- 上下文太短
- 检索时召回片段缺少完整语义

所以它会再做一轮贪心合并：

1. 先拿当前片段做 current。
2. 试着把下一个片段拼上去。
3. 如果合并后的估算长度不超过目标值，或者虽然超过目标值但仍不超过最大值且 current 还偏小，就允许合并。
4. 不能合并时再落成一个 chunk。

这意味着 Argus 当前策略并不是死板地追求“每块都严格 240”，而是更倾向于：

- 在不超预算的前提下，尽可能让 chunk 更完整

---

## 13. 第七步：构造最终 chunk，并追加 overlap

入口方法：

- `buildDocuments(Document source, List<ChunkRange> ranges)`
- `overlapStart(int start, int sectionStart)`
- `buildDocument(Document source, Range range, String sectionPath, int chunkIndex)`

### 13.1 overlap 是怎么加的

第一块不加 overlap。

从第二块开始，会把 chunk 起点往前回退：

```text
start - overlapTokens * CHARS_PER_TOKEN
```

在 dev 环境里，因为 overlap 配置是 32，当前近似含义就是：

- 后一个 chunk 会向前多带约 32 个字符

### 13.2 overlap 不会越过本 section 起点

它还会做一个保护：

- overlap 起点不能早于当前 section 的开始位置

也就是说，当前 overlap 只在本 section 内回退，不会跨 section 倒卷。

这说明它想解决的是“相邻 chunk 语义衔接”，而不是“跨章节混合内容”。

### 13.3 最终 chunk 会附带哪些元数据

`buildDocument(...)` 当前会往 metadata 里写：

- `sectionPath`
- `charStart`
- `charEnd`
- `chunkStrategy`

同时 chunk 的 ID 会基于原文档 ID 再拼接 chunkIndex，形成类似：

```text
sourceId:0
sourceId:1
sourceId:2
```

这让每个 chunk 都具备明确的可追踪性。

---

## 14. 第八步：切好后如何落库

算法输出的是 Spring AI `Document` 列表，不是数据库实体。

真正负责落库的是：

- `ChunkService.saveChunkDocuments(...)`

它会继续完成 4 件事：

1. 把 chunk `Document` 转成 `DocumentChunkEntity`
2. 计算或回收字符范围信息
3. 生成 `chunkSummary`
4. 组装 `metadataJson` 后批量写入 `document_chunks`

所以从职责划分看：

- `StructureAwareChunkTransformer` 负责“怎么切”
- `ChunkService` 负责“怎么保存成系统资产”

这个分层是合理的，因为它把算法决策和数据落地分开了。

## 15. 用一个例子理解整套切片

假设 parser 和清洗之后得到的正文类似这样：

```text
# 产品概述

这是产品整体介绍第一段。

这是产品整体介绍第二段。

## 安装步骤

第一步，准备环境。第二步，下载依赖。第三步，启动服务。

## 常见问题

问题一：无法启动怎么办？
答案：检查端口占用。

问题二：上传失败怎么办？
答案：检查对象存储配置。
```

如果这份文本整体不大，可能直接切成 3 个 section 级 chunk：

1. `产品概述`
2. `安装步骤`
3. `常见问题`

如果 `常见问题` 这一节特别长，超过 `maxTokens`，则会继续往下走：

1. 先按段落拆
2. 某一段还大，再按句子拆
3. 句子再太长，才按预算硬切
4. 拆完后再尽量往回合并到接近目标大小
5. 后续 chunk 起点再向前带一小段 overlap

所以你可以把它理解成：

- 优先让 chunk 和章节结构对齐
- 结构实在太大，再逐层细化

## 16. 这套实现的优点

从当前项目目标看，这套方案有 6 个明显优点：

1. 比固定长度切片更贴近文档自然结构。
2. 对 Markdown 文档、说明文档、规约文档、知识库文章比较友好。
3. 代码块保护避免了技术文档被错误按 `#` 切坏。
4. overlap 能减少边界信息丢失。
5. 元数据完整，后续检索回溯和高亮定位更容易做。
6. 实现规则清晰、可解释性强，便于维护和面试表达。

---

## 17. 当前边界与限制

这套实现虽然合理，但要看清它的边界：

### 17.1 token 估算是字符近似，不是真实 tokenizer

当前：

- `estimateTokens(text) = text.length()`

所以严格意义上，它不是“按模型 token 精确切片”，只是“按字符规模做预算控制”。

### 17.2 标题结构主要依赖 Markdown 风格文本

如果 parser 输出的不是带标题层次的文本，而是一整段纯文本，那么结构切片优势会下降，策略会更多依赖段落和句子切分。

### 17.3 句子边界识别仍然是规则型，不是 NLP 级别分句

当前只按固定标点判断句边界，没有做更复杂的缩写、特殊格式、表格、项目符号识别。

### 17.4 overlap 只在 section 内回退

这能避免跨章节混淆，但也意味着 section 边界如果切得过硬，跨章节衔接信息不会被带进去。

### 17.5 不同文档类型还没有采用差异化切片策略

当前不区分：

- FAQ
- 表格型文档
- API 参考文档
- 代码说明文档

都统一走这套结构感知规则。

---

## 18. 为什么当前阶段这套方案是合理的

如果站在 Argus 当前阶段看，我认为保留这套切片是合理的，原因不是“它最先进”，而是它在工程上平衡得比较好：

1. 实现复杂度低于语义切片。
2. 可解释性明显强于黑盒式动态切片。
3. 对当前支持的 Markdown / TXT / PDF / DOCX 转文本场景足够实用。
4. 配置化程度已经够用，后续可以继续调参。
5. 元数据链路完整，后面要做检索解释、召回定位、命中高亮都更方便。

所以对当前项目来说，它更像是一个“工程上稳、可继续迭代”的默认方案。

---

## 19. 口语化讲法

如果后面你要给别人讲这套实现，可以直接用下面这段：

Argus 目前的文档切片不是按固定长度一刀切，而是优先保留文档结构。它会先按 Markdown 标题拆章节，章节过大再按段落拆，段落过大再按句子拆，最后才按长度预算硬切。拆完之后还会再做一轮合并，让 chunk 尽量接近目标大小，并通过 overlap 保留前后文衔接。最终每个 chunk 都会带上 sectionPath、字符范围和策略标识，再落到 document_chunks，供后续向量检索和混合检索使用。

---

## 20. 最后一句话

如果把当前实现压缩成一句最准确的话：

Argus 当前的文档切片，本质上是一套面向文档结构的分层规则切片器，核心目标不是把文本平均切碎，而是在 token 预算约束下尽量保留章节、段落和句子的自然语义边界。
